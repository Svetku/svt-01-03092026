# Техническое видение

Короткий технический проект LLM-ассистента в Telegram. Цель — проверить идею диалога с ролью из системного промпта. Только необходимое.

## 1. Технологии

| Задача | Выбор |
|---|---|
| Язык | Python 3.12 |
| Зависимости | `uv` + `pyproject.toml` |
| Telegram | `aiogram`, long polling ([ADR 001](adr/001-aiogram-polling.md)) |
| LLM | официальный клиент `openai`; провайдер переключается через `.env` (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`) |
| Сборка и запуск | `make` (`make install`, `make run`) и Docker ([ADR 002](adr/002-docker.md)) |

На старте нет webhook, базы, очереди, кэша и фреймворков агентов.

Конкретный провайдер LLM не фиксируем: достаточно совместимого API и смены трёх переменных в `.env`. В коде нет ветвления по имени провайдера.

## 2. Принципы разработки

- **KISS** — самое простое решение для сценария «сообщение → ответ».
- **СРП** — один класс делает одну вещь, один класс — один файл.
- Прямой поток: Telegram → бот → LLM → ответ. Без лишних слоёв.
- Секреты не в коде.
- Если можно не добавлять сущность — не добавляем.

На этом этапе нет абстракций «на вырост», нескольких ролей, меню, памяти между перезапусками, базы, кэша, очереди, webhook, тестов, линтеров и CI. Команды только `/start` и `/reset`.

Граница проекта: один бот, одна роль из системного промпта, диалог в рамках сессии процесса.

## 3. Структура проекта

Плоская схема. Один класс — один файл. Код бота только в `src/bot/`.

```
.
├── docs/
├── src/bot/
│   ├── main.py              # точка входа, запуск polling
│   ├── config.py            # настройки
│   ├── message_handler.py   # входящее сообщение → ответ
│   ├── llm_client.py        # запрос к модели
│   └── dialog_memory.py     # история диалога в памяти процесса
├── prompts/
│   └── system.txt           # системный промпт / роль
├── pyproject.toml
├── Makefile
├── Dockerfile
└── .env.example
```

`docs/` — идея, видение, ADR. Промпт отдельно от кода, чтобы менять роль без правок Python.

## 4. Архитектура

Линейный поток. Один класс — один файл. Без слоёв, очередей и интерфейсов «на вырост».

```
Telegram
    │  long polling
    ▼
main              — создаёт бота и включает polling
    │
    ▼
message_handler   — принял текст, собрал ответ, отправил назад
    │
    ├── dialog_memory — история этого чата в памяти процесса
    └── llm_client    — системный промпт + история + новое сообщение → модель
            │
            ▼
     OpenAI-совместимый провайдер
```

`config` читается один раз при старте и отдаёт настройки тем, кому нужно.

| Часть | Делает |
|---|---|
| `main` | создаёт бота и включает polling |
| `message_handler` | связывает Telegram, память и LLM |
| `dialog_memory` | хранит реплики, пока процесс жив |
| `llm_client` | один запрос к модели, один ответ |
| `config` | токен Telegram и `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` |

## 5. Модель данных

Базы нет. Только то, что нужно для одного ответа.

**Реплика** — `role` (`user` / `assistant`) и `content` (текст).

**Диалог** — в памяти процесса: ключ `chat_id` из Telegram, значение — список реплик.

Системный промпт в историю не кладём: он живёт в `prompts/system.txt` и каждый раз добавляется к запросу в `llm_client`.

После перезапуска бота история обнуляется.

Чтобы запрос к модели не разрастался, храним только последние 20 реплик чата.

## 6. Работа с LLM

Один класс `llm_client`, один метод «спросить модель».

Запрос каждый раз собирается так:

1. системный промпт из `prompts/system.txt` (роль ассистента);
2. последние реплики чата из `dialog_memory`;
3. новое сообщение пользователя.

Клиент `openai` вызывается с `LLM_BASE_URL`, `LLM_API_KEY` и `LLM_MODEL` из конфига. Ответ — обычный текст: его отправляем в Telegram и кладём в историю.

Нет стриминга, инструментов, нескольких моделей сразу и сложной стратегии повторов. Если провайдер не ответил — пишем ошибку в лог и коротко говорим пользователю, что сейчас ответить не получилось.

## 7. Сценарии работы

Команды обрабатывает тот же `message_handler`. Отдельный класс и кнопки меню не нужны.

**Запуск.** `make run` или контейнер читает `.env` и `prompts/system.txt`, включает polling.

**`/start`.** Короткое приветствие: бот на связи, можно задать вопрос. Историю не трогает. К модели не ходим.

**`/reset`.** Очищает историю этого `chat_id` в `dialog_memory`. Пользователю — короткое подтверждение. К модели не ходим. Другие чаты не затрагиваются.

**Вопрос.** Пользователь пишет текст → реплика в память → `llm_client` спрашивает модель → ответ уходит в чат и в историю.

**Нетекстовое сообщение** (фото, стикер, голос). В чат не отвечаем, в историю не пишем. В лог — `chat_id` и тип вложения.

**Ошибка LLM.** В чат — короткая фраза, что сейчас ответить нельзя. Этот текст в историю не пишем.

Перезапуск процесса по-прежнему обнуляет всю память. Для одного чата достаточно `/reset`.

## 8. Конфигурирование

Все настройки — из `.env`. В репозитории только `.env.example` с именами переменных, без значений. Класс `config` читает файл один раз при старте.

Обязательные переменные:

| Переменная | Смысл |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен бота |
| `LLM_BASE_URL` | адрес OpenAI-совместимого API |
| `LLM_API_KEY` | ключ провайдера |
| `LLM_MODEL` | имя модели |

Провайдер меняется сменой `LLM_BASE_URL`, `LLM_API_KEY` и `LLM_MODEL`. Значений в коде нет. В Docker-образ `.env` не копируется: контейнер читает его снаружи.

## 9. Логирование

Стандартный `logging` Python, вывод в stdout. Уровень `INFO`. Отдельных файлов, ротации и сторонних библиотек нет. Локально строки видны в терминале, в Docker — через `docker logs`.

Пишем:

- старт бота;
- `/start` и `/reset` (с `chat_id`);
- нетекстовое сообщение: `chat_id` и тип вложения (фото, стикер, голос и т.п.);
- ошибка вызова LLM.

Не пишем: токены, ключи, полный текст переписки.

## 10. Сборка и деплой

Две равноправные команды запуска, обе через `make`:

| Команда | Как работает |
|---|---|
| `make run` | без Docker: бот из локального Python / `uv`, настройки из `.env` |
| `make docker-run` | в Docker: один контейнер, `.env` снаружи |

Перед первым запуском:

- без Docker — `make install` (`uv sync`);
- с Docker — `make docker-build` (один образ).

Один `Dockerfile`, один процесс с long polling. Нет CI, облака и оркестрации: деплой — собрать образ и запустить контейнер там, где есть Docker. См. [ADR 002](adr/002-docker.md).
